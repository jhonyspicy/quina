# 大会状態をDurable Objectsで管理し、初期の技術構成をCloudflare中心にする

日付: 2026年10月2日

状態: 採用済み・未実装

## 背景

[大会単位のリモコン・サイネージ接続と進行操作](../../openspec/changes/tournament-remote-signage/spec.md)を実装するにあたり、大会状態の管理元、同期の通信基盤、永続化、言語・ビルド構成などが未決定だった。同仕様は、操作の重複計上の防止、複数端末から届いた開始の扱い、大会単位での状態・履歴の分離、再読み込み・再接続時の最新状態への復帰、リモコン識別番号の維持を求めている。

試作版 `poker-blind-timer` はAblyによるメッセージ配信と端末側のIndexedDBを使っていたという会話上の背景がある。Ablyはメッセージを配信するが大会の状態は持たないため、上記の要件を満たすには状態の管理元を別に用意する必要がある。

開発者は当面一人だが、2〜3人での開発を想定する。

## 検討した選択肢

### 大会状態の管理元と同期

- Cloudflare Workers と Durable Objects（DO）。大会ごとに1つのDOが状態を持ち、各端末とWebSocketで接続して配信する。
- Ablyを継続し、状態の管理元としてAPIとDBを別に用意する。試作版の知見を活かせるが、配信と状態管理が別サービスとなり、両者の整合を自前で扱う必要がある。
- Firebase・SupabaseなどのマネージドDBとRealtime機能。バックエンドの記述は減るが、重複防止や開始の一意性などの業務ロジックをルールや関数で扱う必要がある。

### 大会をまたぐデータの永続化

- Cloudflare D1。DO・Workersと同じ基盤にまとまり、ローカルでもwranglerが再現する。
- マネージドPostgreSQL（Neonなど）をHyperdrive経由で使う。地理空間検索など将来の拡張に強いが、利用するサービスが増える。
- 今回は決めず、店舗・アカウント・課金の実装時に決める。

### 言語・パッケージ管理・フロントエンド・配信

- パッケージマネージャー: pnpm、bun、npm。
- remote・signageのフロントエンド: React + Vite、Svelte + Vite、Next.js。
- 配信先: Cloudflare、Vercelなど別サービス、決定の先送り。

### 開発環境の差の抑制

- バージョン固定とCIで環境をそろえる。
- 最初からDockerまたはDev Containerでの開発を前提にする。

## 判断と理由

### 大会状態はDurable Objectsを正とする

Cloudflare Workers と Durable Objects を採用し、進行中の大会の状態は大会ごとのDOを唯一の正とする。リモコンとサイネージは、Workersを入口として自分の大会のDOにWebSocketで接続する。Ablyは採用しない。

DOは同じIDに対して1つだけ存在し、同じDOへの処理を順番に実行するため、二重開始の防止、操作IDによる重複計上の防止、大会単位の状態分離、接続時の最新状態の送信を1か所で扱える。状態の保存と配信が同じDOにまとまり、保存と配信の不整合を別サービス間で扱う必要がない。

DOが持つ対象は、時計の基準（開始時刻・残り時間・停止状態・現在レベル）、エントリー数とその追加・取り消し、操作履歴、接続中の端末とリモコン識別番号とする。毎秒の表示は各表示端末が受信した基準から計算し、DOは時刻を毎秒配信しない。これにより、表示端末は通信切断中も受信済みの情報で時計を進められる。

WebSocket接続を保ったまま待機中の課金を抑えるため、DOのWebSocket Hibernation APIの利用を前提にする。

### 大会をまたぐデータはD1で管理する

店舗、アカウント、契約・クーポン、大会の登録情報など、大会をまたぐデータはCloudflare D1で管理する。DO・Workersと同じ基盤にまとまり、ローカル開発でもDBサーバーを別に立てる必要がないため。

D1は1データベースの処理を順番に実行し、アプリの処理をはさむ対話的なトランザクションを持たない。複数の文をまとめて実行できるのは `batch()` に限られる。このため、次の方針をとる。

- 一回限りのクーポンコードの使用など、条件を確認して更新する処理は、条件付きの単一SQLまたは `batch()` で一度に判定する。
- 店舗ごとの大会同時実行数の制限のように、数えて判断する処理はD1だけに頼らず、店舗単位のDOなどで直列化する。具体方式は実装時に決める。
- D1作成時に地域の希望（location hint）をアジア太平洋に指定する。

### 言語・パッケージ管理・フロントエンド・配信

- 言語はTypeScriptで統一する。
- パッケージマネージャーはpnpmとし、pnpm workspacesで `apps/` と `packages/` を管理する。依存の書き漏れを検出でき、アプリ間でソースを直接参照しないという[README](../../README.md)の方針を守りやすいため。
- `apps/remote` と `apps/signage` はReact + ViteのSPAとする。いずれも画面遷移の少ないアプリでSSRやSEOを必要としないため。`apps/web`（メインサイト）の構成は本判断の対象外とし、必要になった時点で決める。
- 配信先はCloudflareとし、Workersの静的アセット配信で各アプリを独立してデプロイする。`apps/api` もCloudflare Workersとしてデプロイし、DOとD1を利用する。

### 開発環境はバージョン固定とCIでそろえる

Node.jsのバージョンを `.tool-versions` で固定し（asdf・mise互換）、pnpmのバージョンを `package.json` の `packageManager` で固定してCorepackで導入する。lockfile（`pnpm-lock.yaml`）をコミットし、CIでも同じバージョンでテストする。

Dockerは必須にしない。本番はCloudflare上で動くためコンテナでは本番を再現できず、`wrangler dev` が本番と同じ実行エンジン（workerd）とD1・DOをローカルで再現するため。Windowsの開発者が加わる場合など、必要になった時点でDev Containerを任意の選択肢として追加する。

## 影響

- 試作版のAbly通信部分はQuinaへ移植しない。時計計算や演出など、独立したロジックの選択的な再利用は引き続き検討できる。IndexedDBの利用有無は本判断では決めない。
- Cloudflareへの依存が強まる。D1はSQLite互換のため、他のDBへの移行はPostgreSQL固有機能に依存した場合より行いやすい。
- D1のデータベース容量には上限がある（2026年10月時点で有料プラン10GB、無料プラン500MB）。当面の店舗・契約データには十分だが、将来の大会検索や交流機能でデータが増えた場合は分割などを検討する。D1には地理空間検索の拡張がなく、「近くの大会」検索は緯度経度の範囲指定などで実装するか、その時点で再検討する。
- 料金と無料枠はCloudflareのプラン条件に従う。2026年10月時点では、無料プランでもSQLiteを保存先とするDOを利用できる。
- `docs/architecture/` は、本判断に基づく実装を行う際に作成・更新する。

本判断で決めない事項は次のとおり。

- 未接続の表示端末がPINを表示している間の接続先（PIN管理用のDOなど）、PINの発行方式。
- 表示端末と管理元の時刻のずれの補正方法、同期の許容遅延、競合操作の処理規則。
- 店舗単位の同時実行数を数える具体方式。
- 管理画面側の認証方式、ORMの選定、Google TVアプリの実装方式、`apps/web` の構成。

テストツール（Vitest）とCIサービス（GitHub Actions）は、2026年10月2日のモノレポ整備時に採用し、[アーキテクチャ概要](../architecture/overview.md)に記した。
