# テーマの素材をGitで管理せず、R2に内容のハッシュで保存してlockファイルで参照する

日付: 2026年10月8日

状態: 採用済み・未実装

## 背景

サイネージには、大会の趣旨に合わせたテーマを追加していく方針がある（[プロダクト方針 — テーマと収益化](../product-vision.md#テーマと収益化)）。テーマには背景動画などの大きな素材が含まれ、テーマが増えるほど素材も増える。記録時点でテーマと素材はまだ実装していない。

素材をGitのリポジトリで管理すると、次の問題がある。

- リポジトリの容量が増え続け、cloneやCIが遅くなる。動画は差分を取れず、差し替えるたびに丸ごと履歴に残る。
- サイネージはWorkersの静的アセットとして配信しており（[環境とデプロイ](../architecture/environments.md)）、静的アセットには1ファイルあたりの容量上限（25MiB）がある。背景動画は上限を超えやすく、Gitで管理しても配信は別の場所に置く必要がある。
- `main` へのpushごとにStagingへデプロイするため、素材を同梱するとビルドとデプロイが毎回重くなる。

一方、デプロイはGitHubのブランチのマージをきっかけに行う。素材をGitに含めない場合、開発者のローカルにしかない素材を、マージ後のCIがどこかへ運ぶことはできない。

## 検討した選択肢

### 素材の置き場所

- Gitで直接管理する。
- Git LFSで管理する。GitHubのLFSは容量と転送量に上限があり、配信の容量上限の問題も残る。
- Cloudflare R2に置く。Workers・Durable Objectsと同じ基盤にまとまり、データ転送料（egress）がかからない。
- Cloudflare Stream。画質の自動切り替えができるが、ループ再生する背景動画には過剰で、利用するサービスが増える。

### 素材をR2へ上げる時期

- A: デプロイ時にCIがR2へ上げる。素材がGitにないため、CIは素材を持っていない。
- B: 開発者がPRを出す前にR2へ上げ、Gitには素材を特定する情報（lockファイル）だけをコミットする。
- C: 管理画面からzipでテーマを追加する。ログイン・管理画面が未実装のため、現時点では採れない。

### R2での素材の名前と環境の分け方

- 素材の内容のハッシュを名前（キー）にし、上書き・削除しない。全環境で1つのバケットを共有する。
- テーマ名とファイル名をキーにし、環境ごとにバケットを分けて、昇格時にコピーする。

## 判断と理由

### 素材はR2に置き、テーマのコードはGitで管理する

テーマのレイアウトや演出のコードはGitで管理し、動画・画像などの素材だけをR2に置く。素材は `.gitignore` でGitの管理から外す。

### 開発者がPRの前にR2へ上げ、lockファイルで参照する（B）

開発者はローカルに素材を置いて動作確認し、アップロード用のコマンドでR2へ上げる。コマンドは各素材のハッシュを記したlockファイルを書き出し、開発者はlockファイルとテーマのコードをコミットする。

デプロイで運ぶのはコードとlockファイルだけで、素材はマージ前にR2にある。このため、ブランチのマージでデプロイする流れのままで、ローカルにしかない素材を運ぶ問題が生じない。上げ忘れは、lockファイルの各素材がR2にあるかをCIで確かめて防ぐ。

将来、管理画面からテーマを追加する方式（C）に進んだ場合も、lockファイルの代わりにD1のテーマ登録情報がハッシュを持つだけで、R2側の構成は変えずに済む。

### 内容のハッシュをキーにし、全環境で1つのバケットを共有する

R2のキーは素材の内容のSHA-256から決め、一度置いた素材は上書き・削除しない。

- 同じキーの中身が変わらないため、CDNやブラウザに長期間キャッシュさせても、古い素材が表示され続けることがない。
- 素材が追加されるだけなので、Stagingと本番で同じ素材を共有しても互いに影響しない。環境ごとにバケットを分けて昇格時にコピーする手間が要らない。
- 同じ内容の素材は1つにまとまる。

R2には版の管理機能がないが、上書き・削除しない運用のため、R2を素材の正本としてよい。権利侵害や誤った投稿などで公開を止める必要がある場合に限り、例外として削除する。

### 素材はURLを知っていれば誰でも読める形で公開する

店舗専用テーマを含め、素材は利用権限を確かめずに公開する。店舗専用テーマの利用条件（[店舗専用テーマの利用条件](../../openspec/changes/store-exclusive-theme/spec.md)）は、テーマを選んで使えるかどうかに適用し、素材そのものの秘匿には適用しない。

店舗専用テーマの素材は、ドリンクやフードのメニューなど店舗の宣伝を想定しており、外部に知られて困る情報を扱わない。素材のURLは内容のSHA-256を含むため推測できないが、URLが共有されれば誰でも読める。この前提を利用規約で利用者に示し、機密情報を素材に含めないよう求める。

利用権限を確かめて配信する方式（Workerでの確認、期限付きのURL）は、配信の処理が増え、長期キャッシュとも両立しにくいため採用しない。

## 影響

- 素材の正本はR2になり、ローカルの素材はその複製として扱う。別の開発者・別のPCでは、lockファイルをもとにR2から素材を取得する。
- R2へ書き込むのは素材を追加する開発者だけで、CIは素材の存在確認に読み取りだけを使う。
- どのlockファイルからも参照されない素材（マージされなかったPRの素材など）がR2に残る。削除する仕組みは必要になった時点で用意する。
- 素材は公開されるため、Stagingのアクセス制限（Cloudflare Access）の対象外となる。
- 利用規約に、素材がURLを知っていれば誰でも読めることと、機密情報を素材に含めないことを記す。利用規約は未作成。
- 優勝者の記念撮影の写真など、個人の情報を含みうるものを将来扱う場合は、本判断の公開の方針をそのまま適用せず、別途判断する。
- 配信のホスト名・方法、lockファイルの形式などの詳細は本判断では定めない。要件・受け入れ条件・未決定事項は[テーマ素材のR2管理の変更仕様](../../openspec/changes/theme-assets-r2/spec.md)に記録する。
- 管理画面からzipでテーマを追加する方式は将来の可能性であり、採用・実装は決まっていない。
