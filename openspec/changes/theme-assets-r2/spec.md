## 変更の目的と範囲

サイネージのテーマで使う動画・画像などの素材をGitで管理せず、Cloudflare R2に置く。ブランチのマージでデプロイする流れを変えずに、ローカルで追加した素材を各環境で使えるようにする。

範囲は、素材のアップロード・取得・参照・配信と、上げ忘れの検出までとする。次の内容はこの仕様で決定しない。

- テーマの表示や切り替えの仕組み、テーマのデータモデル。記録時点でテーマは未実装で、この仕様は最初のテーマを実装する際の素材の扱いを定める。
- テーマの利用条件（プラン・店舗専用テーマ）の判定。[店舗専用テーマの利用条件](../store-exclusive-theme/spec.md)を参照する。
- 管理画面からzipでテーマを追加する方式。将来の可能性であり、採用・実装は決まっていない。

## 流れ

```text
① ローカルで動作確認        ② アップロード（開発者が実行）       ③ PR → マージ → デプロイ
<テーマ>/assets/bg.mp4  ──→  R2: 内容のSHA-256をキーに保存     コードとlockファイルだけが流れる
  （Gitの管理外）            lockファイルを更新してコミット      CIがR2に素材があるかを確認する
```

## 確定した要件

### 素材とGitの関係

- テーマの素材はGitで管理しない。素材を置くディレクトリを `.gitignore` に記す。
- テーマのコードと、素材を特定するlockファイルはGitで管理する。
- lockファイルは、テーマのコードが使う素材の名前（例: `background`）ごとに、内容のSHA-256、MIMEタイプ、バイト数を記す。テーマのコードは素材を名前で参照し、URLはlockファイルのハッシュから組み立てる。

lockファイルの例（形式は未決定）:

```json
{ "background": { "sha256": "9f3a…c1", "type": "video/mp4", "size": 48213992 } }
```

### R2への保存

- 素材は全環境（ローカル・Staging・本番）で共有する1つのR2バケットに置く。
- R2のキーは素材の内容のSHA-256から決める。テーマ名やファイル名をキーに含めない。
- 一度置いた素材は上書き・削除しない。権利侵害や誤った投稿などで公開を止める必要がある場合に限り、例外として削除し、CDNのキャッシュも消す。

### アップロード（開発者のコマンド）

- 開発者が実行するコマンド（例: `pnpm theme:upload <テーマ>`）で、テーマの素材をR2へ上げ、lockファイルを書き出す。
- 各素材のSHA-256を計算し、同じキーがR2にあれば上げ直さない。
- アップロード時にMIMEタイプをR2の素材に記録する。
- R2へ書き込む権限は開発者の手元の認証（`wrangler login` など）を使う。書き込み用のトークンをリポジトリやCIに置かない。

### 取得（別の開発者・別のPC）

- lockファイルをもとに、R2から素材をローカルの素材ディレクトリへ取得するコマンド（例: `pnpm theme:pull`）を用意する。取得した素材はSHA-256を確かめる。

### ローカルでの動作確認

- サイネージの開発サーバーは、ローカルに素材があればそれを使う。ローカルにない場合の扱い（R2から読むか、取得を促すか）は未決定。
- アップロード前でも、ローカルに置いた素材でテーマの動作を確認できる。

### 上げ忘れの検出

- CIで、全テーマのlockファイルに記された素材がR2にあるかを確かめ、ない場合は失敗させる。PRの段階で検出し、素材のないままマージされることを防ぐ。
- CIは読み取りだけを行い、R2へ書き込まない。

### 配信

- 各環境のサイネージは、lockファイルのハッシュから組み立てたURLで素材を読む。
- 素材の中身は同じURLで変わらないため、長期間キャッシュさせる（`Cache-Control: public, max-age=31536000, immutable` 相当）。
- Workersの静的アセット（`dist/`）に素材を含めない。

### 公開範囲と利用規約

- 素材は、店舗専用テーマのものを含め、URLを知っていれば誰でも読める形で公開する。素材の配信で利用権限を確かめない。
- 店舗専用テーマの利用条件は、テーマを選んで使えるかどうかに適用する。素材そのものを利用条件どおりに秘匿することはしない。
- バケットの素材の一覧は公開しない。素材のURLは内容のSHA-256を含み、推測できない。
- 店舗専用テーマの素材は、ドリンクやフードのメニューなど店舗の宣伝を想定し、機密情報を扱わない。
- 利用規約に、素材がURLを知っていれば誰でも読めること、機密情報を素材に含めないこと、素材が外部に知られた場合の責任を負わないことを記す。具体的な文言は利用規約の作成時に決める。
- 優勝者の記念撮影の写真など、個人の情報を含みうるものは、この公開の方針の対象外とし、扱う場合は別途決める。

## 受け入れ条件

以下は将来の実装時に確認する条件であり、検証済みではない。

| 状況 | 期待する結果 |
| --- | --- |
| ローカルに素材を置き、アップロード前に開発サーバーで確認する | 置いた素材でテーマが表示される |
| 新しい素材をアップロードする | R2に内容のSHA-256をキーとして保存され、lockファイルに名前・ハッシュ・MIMEタイプ・バイト数が記される |
| 同じ内容の素材を再度アップロードする | R2へ上げ直さず、lockファイルは変わらない |
| 素材を差し替えてアップロードする | 新しいキーで保存され、元の素材はR2に残る。lockファイルは新しいハッシュに変わる |
| `git status` を確認する | 素材のファイルは表示されず、lockファイルとテーマのコードだけが変更として表示される |
| アップロードせずにlockファイルを手で書き換えたPRを出す | CIの素材確認が失敗する |
| アップロード済みのPRをマージする | Stagingへのデプロイで素材を運ばず、デプロイ後のサイネージで素材が表示される |
| 別のPCでcloneし、取得コマンドを実行する | lockファイルどおりの素材がローカルに揃い、ハッシュが一致する |
| デプロイ後のサイネージで素材を読み込む | 長期キャッシュを許すヘッダーで配信される |
| 店舗専用テーマの素材のURLを、Cloudflare Accessの認証もログインもしていないブラウザで開く | 素材を読める |
| バケットのルートなど、素材の一覧を得ようとする | 一覧は返らない |

## 未決定事項

- 素材の配信方法とホスト名。素材を公開すると決めたため、R2のCustom Domain（例: `assets.quina.poker`）で公開する案が有力。サイネージと同じホスト名の配下でWorkerがR2から返す案は、サイネージのWorkerが静的ファイルだけを配信する現在の構成を変える。どちらの案でも、素材はStagingのCloudflare Access（[ADR 0005](../../../docs/adr/0005-staging-environment-and-same-origin-api.md)）の対象外とする。
- バケット名と、ローカル開発での読み先（本物のバケットか、wranglerのローカル環境か）。
- CIの素材確認の方法。素材は公開されるため、認証なしで確認できる見込み。
- 公開を止めるために素材を削除する際の手順と、削除を判断する人。
- 利用規約の具体的な文言と、利用規約の作成時期。利用規約自体が未作成。
- テーマのコードと素材を置くディレクトリ（例: `apps/signage/themes/<テーマ>/`）。サイネージ以外のアプリ（リモコンでのテーマ選択の見本表示など）でも素材を使う場合の置き場所。
- lockファイルの名前・形式、R2のキーに拡張子を含めるかどうか。
- 素材の容量上限と、動画の形式（コーデック・解像度・ビットレート）の推奨値。
- サイネージで素材を端末に保存し、通信切断中も演出を続けるかどうか（Service Worker・Cache APIなど）。
- どのlockファイルからも参照されない素材を削除する仕組みの要否と方法。
